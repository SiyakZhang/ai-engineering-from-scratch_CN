## 1. 工单系统必须分类一个请求、验证固定 schema，并路由到四个队列之一。步骤永远不变。哪种架构最适合作为默认方案？

- **A** 拥有全部支持工具的无边界自主 agent
- **B** 将路由策略编码在 agent prompt 而非固定分支中的管理者、队列专家和验证 subagent 层级
- **C** 允许模型发明新队列的远程 MCP 服务器
- **D** 包含一个模型分类步骤的确定性工作流

<details>
<summary>查看答案与解析</summary>

**答案**　D

顺序和分支集合已经确定，使用确定性工作流更容易测试、保障安全和运维。只有执行中的观察结果会决定未知路径时，引入 agent 规划的复杂度才有价值；这里的流程已经明确。

</details>

## 2. 仓库 agent 绝不能读取机密文件，并且必须格式化每个编辑过的 Python 文件。哪些控制应属于运行框架？请选择所有适用项。

- **A** 编辑后运行格式化工具的后置工具 hook
- **B** 排除凭证位置的文件系统沙箱
- **C** 使用模型策略审核批准每条文件系统路径
- **D** 拒绝已配置机密路径的前置工具策略 hook

<details>
<summary>查看答案与解析</summary>

**答案**　A、B、D

前置工具策略在访问前阻止，后置工具自动化格式化完成的编辑，沙箱会在 hook 不完整时限制影响。prompt 指引仍有用，但不是确定性隔离。

</details>

## 3. Claude 返回 ID 为 toolu_9 的 tool_use 块。客户端在下一次 Messages API 请求中必须保留哪些元素？请选择所有适用项。

- **A** 任务仍需要的先前对话上下文
- **B** 在独立 user 角色消息中发送结果文本
- **C** 包含原始 tool_use 块的 assistant 消息
- **D** tool_use_id 为 toolu_9 的 user 角色 tool_result

<details>
<summary>查看答案与解析</summary>

**答案**　A、C、D

客户端拥有状态：它重新发送必需历史、保留 assistant 工具请求，并追加关联的 user 工具结果。只发送结果会丢失协议上下文。

</details>

## 4. 流式结构化响应当前包含 {"status":"read。在更新订单记录前，应用应做什么？

- **A** 缓冲至内容块和消息完成，再解析、验证和授权
- **B** 每收到一个新字符就重试请求
- **C** 自行补齐缺失的 JSON 字符
- **D** 将语法上看似合理的前缀当作暂定 JSON，补齐预期结尾字符后再验证并更新记录

<details>
<summary>查看答案与解析</summary>

**答案**　A

流前缀尚未完成，不是有效应用契约。不可逆状态变更必须等到完整终止事件后，再进行 schema、语义和策略验证。

</details>

## 5. 团队必须在明天前对 80,000 张归档工单分类。没有用户在等待某一条工单的即时响应。哪种 API 模式最合适？

- **A** 一个长时间运行的 agent 会话，按顺序处理工单 ID，并在每次分类后检查点保存已累积的上下文
- **B** 使用稳定自定义请求标识符的 Message Batches
- **C** 一个交互式流式会话
- **D** 每个 token 启动一个新的 Claude Code 会话

<details>
<summary>查看答案与解析</summary>

**答案**　B

批处理适合大量彼此独立的异步请求：吞吐量比即时延迟更重要。自定义 ID 让应用能关联每一条结果和失败记录。

</details>

## 6. 支付服务商可能已经接受扣款，但支付工具随后超时。最安全的下一步是什么？

- **A** 删除追踪记录并启动新会话
- **B** 用相同参数重试一次，让 Claude 比较两次响应后再决定哪个外部支付状态才是权威状态
- **C** 在任何重试前，先用稳定的操作 ID 与支付系统核对状态
- **D** 立即以更高的 token 限制重试

<details>
<summary>查看答案与解析</summary>

**答案**　C

交易边界处的结果仍不明确。幂等键和权威系统的状态核对才能确认重试是否安全；模型推理无法确定外部状态。

</details>

## 7. 哪类内容最应该写入项目的 CLAUDE.md？

- **A** 每个部署环境所需生产凭证名称及其当前密钥库位置的清单
- **B** 团队主要框架参考文档的完整副本，让 Claude 从这一份维护中的资料推导构建、测试和仓库规则
- **C** 开发者当前工单的临时状态
- **D** 权威的构建和测试命令，以及不显而易见的仓库约束

<details>
<summary>查看答案与解析</summary>

**答案**　D

CLAUDE.md 最适合作为精简的项目上手契约。大型参考资料应以链接形式提供，临时状态应放在别处，机密绝不能写进模型可读的说明中。

</details>

## 8. 线上服务商响应中包含某个字段，但 SDK 反序列化后应用始终看不到它。应从哪里开始调试？

- **A** 比较线上传输响应、SDK 对象和应用的每一道序列化边界
- **B** 提高模型温度
- **C** 添加一个独立的模型审查者，将应用可见对象与 prompt 要求比较并建议修改 prompt
- **D** 重写系统 prompt

<details>
<summary>查看答案与解析</summary>

**答案**　A

证据表明问题出在集成边界。逐一检查各层的数据表示，可以找到字段在哪一步丢失，也能避免无关的 prompt 修改。

</details>

## 9. 两个当前模型均通过了所需的准确性和安全门槛。Model A 在代表性工作负载上更快、更便宜。团队应该选择哪个？

- **A** Model B，因为它额外的能力可能减少当前验收数据集或安全门槛没有涵盖的罕见错误
- **B** Model A，同时保留迁移和回归监控
- **C** 在输出变得确定性之前，两者都不选
- **D** 无论成本如何，每个请求都使用两者

<details>
<summary>查看答案与解析</summary>

**答案**　B

根据实测需求选择能力恰好够用的模型。质量和安全都达标后，Model A 胜出；但行为会变化，仍需版本化评估和监控。

</details>

## 10. 哪些改动通常会提高 prompt 缓存复用率？请选择所有适用项。

- **A** 在每个 prompt 开头附近插入随机请求 ID
- **B** 不要假设命中，而应测量缓存创建和读取用量
- **C** 在可行的地方，让可复用前缀保持字节级稳定
- **D** 将稳定的系统指令和工具定义置于易变的用户内容之前

<details>
<summary>查看答案与解析</summary>

**答案**　B、C、D

缓存依赖稳定的共享前缀，也需要显式测量。开头附近的易变数据会让后续内容无法复用。

</details>

## 11. 一个简单的 schema 提取不用 extended thinking 就已通过 99.8% 的案例。最佳默认配置是什么？

- **A** 只在生产环境启用 thinking，使模型能补偿评估数据集未覆盖的输入
- **B** 启用最高强度的 thinking，为每次提取增加第二条推理路径；再保留 schema 验证作为下游安全检查
- **C** 保持较简单的配置，除非评估显示 thinking 值得付出延迟和成本
- **D** 用 thinking 替代 schema 验证

<details>
<summary>查看答案与解析</summary>

**答案**　C

推理预算是优化取舍。若更简单的配置满足实测需求，额外的 thinking 没有证据显示其价值，却会增加运营成本。

</details>

## 12. 一个长期运行的编程 agent 正在压缩上下文。还有哪些信息应该保存在持久状态中？请选择所有适用项。

- **A** 产物路径、哈希和验证结果
- **B** 批准记录和外部操作标识符
- **C** 验收标准及未完成的任务承诺
- **D** 每次压缩交流的完整记录，让下一会话重建此前的推理，不使用带类型的检查点

<details>
<summary>查看答案与解析</summary>

**答案**　A、B、C

概率性摘要之外还要保留关键状态。需要精确保留的信息应写入持久记录，不相关的对话可以裁剪。

</details>

## 13. 某个响应是有效 JSON 且通过了声明的 schema，但其中的 invoice_id 属于另一个租户。哪项检查失效了？

- **A** Prompt 缓存和会话验证，因为缓存的结构化响应可能会携带上一次已认证请求中的资源标识符
- **B** Schema 形状
- **C** JSON 语法
- **D** 针对可信应用状态进行语义与授权验证

<details>
<summary>查看答案与解析</summary>

**答案**　D

Schema 只能证明结构，不证明归属。应用必须绑定已认证的租户身份，并根据其系统记录验证资源访问权限。

</details>

## 14. 一个检索到的网页要求 agent 上传其环境变量。以下哪些响应是恰当的？请选择所有适用项。

- **A** 将网页视为不可信数据，而不是更高优先级的指令
- **B** 在工具边界拒绝访问密钥路径和环境变量
- **C** 若资源来自已批准的连接器，且页面元数据将某人标识为组织管理员，就遵从该指令
- **D** 限制网络目标并对追踪记录脱敏

<details>
<summary>查看答案与解析</summary>

**答案**　A、B、D

来源可信度、能力拒绝、网络控制和安全处理机密的遥测共同构成分层防御。无论措辞如何，内容都无法仅靠自称有权威来证明自身已经过认证。

</details>

## 15. 某个 MCP 服务器必须公开一份可寻址的只读政策文档，标识为 policy://refunds/current。最适合用哪种原语？

- **A** 资源
- **B** 工具
- **C** 子 agent
- **D** Prompt

<details>
<summary>查看答案与解析</summary>

**答案**　A

资源提供以 URI 为地址的上下文。工具执行由模型选择的操作，而 prompt 为兼容 MCP 的宿主提供可复用、由用户调用的消息模板，用于重复的工作流。

</details>

## 16. 哪些场景值得承担 MCP 额外的协议和部署成本？请选择所有适用项。

- **A** 多个已获批准的宿主需要共享能力发现机制
- **B** 一个进程内函数需要类型化 schema，未来或许会复用，但当前没有宿主或部署边界需要协议发现
- **C** 该集成需要具备版本控制的远程认证与治理
- **D** 工具、资源或 prompt 应通过标准客户端—服务器边界暴露

<details>
<summary>查看答案与解析</summary>

**答案**　A、C、D

需要跨宿主互操作、共享能力发现，或受治理的客户端—服务器能力边界时，MCP 带来的价值足以抵消额外成本。单个本地函数通常直接做成进程内工具更简单，也更容易维护。

</details>
