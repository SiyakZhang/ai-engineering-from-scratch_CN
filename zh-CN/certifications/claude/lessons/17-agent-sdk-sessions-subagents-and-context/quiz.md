# Agent SDK Session、Subagent 与上下文 · 自测

每题先选答案，再展开解析。

## 1. agent 应把权威的任务完成状态、批准和外部副作用 ID 存在哪里？

- **A** 存进 session 摘要，以便恢复时保留完成与批准声明
- **B** 存进稳定的 system instruction，其中列出批准和最后已知的副作用 ID
- **C** 存进持久的外部状态，并将引用加载到上下文
- **D** 附在每项已完成操作上的结构化置信度记录中

<details>
<summary>查看答案与解析</summary>

**答案**　C

对话只是工作集。持久状态提供版本控制、对账、幂等性，以及跨 session 或上下文丢失的恢复能力。

</details>

## 2. 什么时候 fork session 比恢复它更合适？

- **A** 没有既有状态，但两个 agent 需要分别写计划时
- **B** 原任务已完成，但其 session 仍需保留作参考时
- **C** 任一外部状态 tool 调用后，继续同一份已对账计划时
- **D** 探索替代方案必须保留原分支并隔离修改时

<details>
<summary>查看答案与解析</summary>

**答案**　D

fork 会保留共同起点，同时允许隔离探索。恢复则是在对账外部状态后，延续一条仍然有效的执行轨迹。

</details>

## 3. 压缩解决什么问题？

- **A** 在保留精简当前工作集的同时缓解上下文大小压力
- **B** 长时间暂停后重新验证用户身份和当前范围
- **C** 跨重启持久记录批准和外部交易
- **D** 核对超时前可能已完成、结果不明的副作用

<details>
<summary>查看答案与解析</summary>

**答案**　A

压缩减少上下文体积。持久状态、授权和副作用对账仍是独立的系统职责。

</details>

## 4. 哪种用途最适合 pre-tool hook？

- **A** 选择哪个未解决假设值得进行下一轮研究
- **B** 阻止声明文件范围之外的写操作
- **C** 反复改写解释，直到评分者认为它足够有说服力
- **D** 根据当前事实判断一条法律条款是否构成实质风险

<details>
<summary>查看答案与解析</summary>

**答案**　B

范围是可在执行前检查的确定性 invariant。语义判断应由模型结合评估和适当审查来完成。

</details>

## 5. 退款请求发出后超时，结果可能已经成功。重试前该做什么？

- **A** 立即用同一键重试，因为相同请求总是安全的
- **B** 用更大模型恢复，再从 session 事件序列推断是否完成
- **C** 核对幂等键与外部结果，判断副作用是否已经发生
- **D** 在本地标记调用失败，再签发新的退款操作标识符

<details>
<summary>查看答案与解析</summary>

**答案**　C

未知结果会让重试重复一项高影响操作。对账能建立当前事实，使下一次操作安全。

</details>

## 6. agent session 暂停后，依赖发生了实质变更。最可靠的继续策略是什么？

- **A** 附上此前全部 tool 日志，让既有上下文无需重新规划就能适应
- **B** 不经对账就从暂停 session fork，以保留原分支
- **C** 恢复旧计划，但要求 agent 在工作时考虑这个依赖
- **D** 重新验证状态、标记陈旧假设，并以全新的结构化计划启动或 fork

<details>
<summary>查看答案与解析</summary>

**答案**　D

实质外部变化会使原执行轨迹失效。用持久的当前状态构建新工作上下文，避免在恢复时强行带入陈旧假设。

</details>
