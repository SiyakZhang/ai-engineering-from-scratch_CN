# Eval 将 Agent 行为变成工程证据 · 自测

每题先选答案，再展开解析。

## 1. agent 声称订单已经发货，但没有 tool 调用，也没有数据库变更。哪个评估维度能发现这一关键失败？

- **A** 用语义 grader 比较该主张与用户要求的结果
- **B** 审查声称执行发货操作的 trajectory
- **C** 根据权威订单系统中的实际记录和状态变更验证最终结果
- **D** 通过协议校验确认响应未使用 tool 且正常结束

<details>
<summary>查看答案与解析</summary>

**答案**　C

权威系统状态能证明操作是否真实发生。流畅的输出无法取代外部状态检查。

</details>

## 2. 哪项属性应该用确定性方式测试，而不是交给 LLM judge？

- **A** 两份内容细致的摘要是否保留了等价的含义与重点
- **B** 文字是否能让读者感受到共情
- **C** 解释是否向新手清楚传达了核心思想
- **D** JSON 是否包含必需字段和有效 enum

<details>
<summary>查看答案与解析</summary>

**答案**　D

schema 有效性具有精确规则。确定性 validator 比模型 grader 更便宜、可复现，也更可靠。

</details>

## 3. 应该如何验证基于模型的 grader？

- **A** 使用独立人工标注样本校准，并审查意见不一致的 case
- **B** 选择能力更强的 grader 模型，并为详细推理提供足够 token
- **C** 重复每次判断，在多个样本结果一致时接受该标签
- **D** 提供 generator 的完整推理，让 grader 重建其意图

<details>
<summary>查看答案与解析</summary>

**答案**　A

人工标注 case 能暴露假阳性、假阴性、rubric 歧义与 grader 偏差。仅靠自洽性无法证明有效。

</details>

## 4. 服务商响应有效，但 SDK client 在序列化期间丢失了一个响应字段。调试时应该检查什么？

- **A** 最终应用 prompt 与模型设置
- **B** 捕获真实线上报文响应，并逐一检查它经过的每个序列化边界
- **C** SDK 的公开类型声明，但不捕获服务商原始响应
- **D** 最终映射对象与下游 consumer，但不检查更早的边界

<details>
<summary>查看答案与解析</summary>

**答案**　B

先比较线上报文数据、SDK 类型与应用映射，就能确定字段在哪里丢失，不必先修改模型行为。

</details>

## 5. 为什么发布 gate 除了平均分，还应检查 slice 与严重故障？

- **A** 只要严重故障对总分的影响低于 gate，就可以接受
- **B** 只有每个 slice 的流量频率相同时，平均分才足够
- **C** 平均分可能掩盖某个领域或安全 case 新出现的严重回归
- **D** slice 能让基于模型的评估足够确定，从而取代严重 case 审查

<details>
<summary>查看答案与解析</summary>

**答案**　C

总体小幅提升可能掩盖数据泄露、跨 tenant 访问，或某个重要场景组的大幅下降。

</details>

## 6. 请求因 tool result 顺序无效而失败。哪种恢复方式最合适？

- **A** 保留相同 client 历史，换用更大的模型重试格式错误的消息
- **B** 让模型 grader 判断预期 tool 序列在语义上是否合理
- **C** 增加 tool 超时，因为延迟的结果可能造成无效 content block 顺序
- **D** 先修复 client 的协议状态，再为该消息顺序和恢复路径补上合约测试

<details>
<summary>查看答案与解析</summary>

**答案**　D

这是确定性的协议缺陷。修改 prompt 或模型无法修复格式错误的应用状态。

</details>
