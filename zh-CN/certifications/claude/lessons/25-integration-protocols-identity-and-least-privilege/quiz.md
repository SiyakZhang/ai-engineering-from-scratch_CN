# 集成协议、身份与最小权限 · 自测

每题先选答案，再展开解析。

## 1. 客服人员只需要读取工单和起草回复，但他们的 agent 还有退款和账户删除工具。哪种做法最能降低风险？

- **A** 把敏感工具调用路由给更大的模型，让它更可靠地判断授权
- **B** 保留可见能力，但要求每项工具说明重复该角色的政策限制
- **C** 从该角色中移除不必要的工具和 scope
- **D** 保留所有工具，但记录敏感调用

<details>
<summary>查看答案与解析</summary>

**答案**　C

最小权限会移除角色不需要的能力。日志和警告可以辅助控制，但不必要的权限和攻击面依然存在。

</details>

## 2. 为什么能力发现和执行授权是两项独立控制？

- **A** 发现机制在会话开始时评估，因此只有目录以外的工具才需要授权
- **B** 发现机制会限制上下文，因此执行授权是多余的
- **C** 发现机制在 host 端过滤能力，而集成协议会自动授权每项已公布的操作
- **D** 隐藏工具能减少暴露，执行授权则能阻止直接调用或使用过期权限的未授权调用

<details>
<summary>查看答案与解析</summary>

**答案**　D

精简目录可以改善选择并减少暴露，但调用方仍可能访问端点，权限也可能变化。服务必须对每次执行进行授权。

</details>

## 3. 什么情况下 MCP 比直接 API 更合适？

- **A** 多个 host 需要跨 server 边界以标准方式动态发现能力时
- **B** 一个稳定服务需要最低延迟时
- **C** 集成需要协议层推断用户身份，并且不经过独立政策服务就授予权限时
- **D** 任意 Claude 应用需要调用工具，并希望用一种协议取代各服务自己的授权时

<details>
<summary>查看答案与解析</summary>

**答案**　A

MCP 额外增加一道协议边界，其价值在于标准化能力发现和跨 host 集成。对于已知的低开销服务调用，直接 API 可能仍然更清晰。

</details>

## 4. 可靠的审批必须与什么绑定？

- **A** 模型置信度、风险分类，以及模型选择拟议能力时给出的理由
- **B** 确切操作、参数、请求方、审批方权限和到期时间
- **C** 工具名称和执行审批的租户
- **D** 当前 prompt 和对话标识符，使该模型轮次内的所有工具调用都继承审批

<details>
<summary>查看答案与解析</summary>

**答案**　B

审批只在特定身份和时间窗口下，对一项明确的预期影响有效。参数变化后必须重新决策。

</details>

## 5. 工具返回授权错误时，agent 框架应该如何分类？

- **A** 把请求路由给更强的模型，让它不断修改工具参数，直到授权成功
- **B** 指数退避后用相同凭证重试，因为授权服务可能暂时不一致
- **C** 除非访问权限或审批状态发生变化，否则不可重试，并提供安全的升级操作
- **D** 把故障记录为工具警告，省略受限影响，然后假装工作流已成功并继续执行

<details>
<summary>查看答案与解析</summary>

**答案**　C

权限或审批状态不变时，重复同一个未授权请求不会成功。结构化错误应该说明安全的下一步，同时避免泄露机密细节。

</details>

## 6. 为什么应用级服务 API key 不足以实现逐用户授权？

- **A** 它会阻止下游审计日志记录应用身份或请求的服务操作
- **B** 它只验证客户端传输，因此无法直接调用下游服务端点
- **C** 它的有效期作用于整个应用，因此在授权检查前，用户请求可能已经超过凭证有效期
- **D** 它标识宽泛的应用权限，但可能不携带真人身份主体、租户或当前 scope

<details>
<summary>查看答案与解析</summary>

**答案**　D

下游服务需要关于实际身份主体和请求操作的可信声明。宽泛的应用凭证会把用户边界压缩成无法强制执行的 prompt 指令。

</details>
