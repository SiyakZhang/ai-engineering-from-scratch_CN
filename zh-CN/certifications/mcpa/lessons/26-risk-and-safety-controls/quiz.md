# MCP 工具调用的风险与安全控制 · 自测

每题先选答案，再展开解析。

## 1. 某网关要求每次破坏性工具调用都由人工确认，并把这当作完整的安全设计。哪种风险仍会原封不动地存在？

- **A** 工具调用超过声明的超时时间，并在连接关闭后返回
- **B** 响应包含多个内容块，而不是恰好一个
- **C** 确认对话框渲染过慢，用户无法阅读其中内容
- **D** 工具描述中早已嵌入一条指令，模型在任何确认发生前便会执行

<details>
<summary>查看答案与解析</summary>

**答案**　D

确认机制只拦截破坏性调用本身；被投毒的描述可能早已影响模型选择哪个调用以及如何填写参数。因此，描述和结果必须在确认步骤之前就按不可信输入处理。

</details>

## 2. 某个已批准工具的名称和经哈希固定的描述都没变，但新的发现响应中，同一工具的 inputSchema 不同。固定完整描述符的网关应如何处理？

- **A** 将工具作为 rug pull 隔离并等待复审，复审前不再允许调用
- **B** 自动接受变化，因为工具名称和描述都没变
- **C** 完全忽略 schema 字段，因为只有描述文本能携带注入指令
- **D** 信任新 schema，因为其注解已将工具标记为只读

<details>
<summary>查看答案与解析</summary>

**答案**　A

只对描述文本计算哈希会漏掉 schema 或注解变化。完整描述符固定可以捕获此类漂移，正确做法是将工具作为 rug pull 隔离，等人工重新批准新描述符及其哈希。

</details>

## 3. 工具处理器需要为当前请求调用无关的上游计费 API，手中已有客户端用于向 MCP 服务器认证的 bearer token。处理器必须怎么做？

- **A** 把同一 bearer token 转发给上游 API，因为它已证明用户通过认证
- **B** 使用单独签发、限定给上游的凭据，而不是转发入站 MCP token
- **C** 缓存入站 token，并在会话今后的每次上游调用中复用
- **D** 去掉 token 的签名，只把剩余 claims 转发给上游

<details>
<summary>查看答案与解析</summary>

**答案**　B

把限定给 MCP 服务器的 token 转发到无关上游 API 属于明确禁止的 token 透传。合规处理器只把入站 token 用于自身验证，并为出站调用使用不同的、限定给上游的凭据。

</details>

## 4. 某工具 inputSchema 的一个属性通过 $ref 指向 https://partner.example/schema.json。按照 2026-07-28 规范，正确处理方式是什么？

- **A** 用空 schema 对象替换 $ref，让验证始终静默通过
- **B** 获取并缓存一次 schema，之后每次验证都信任它
- **C** 默认绝不自动解引用网络地址；将获取操作设为显式选择加入，并置于允许列表之后
- **D** 自动解析引用，因为 JSON Schema 2020-12 要求每个 $ref 都必须解析

<details>
<summary>查看答案与解析</summary>

**答案**　C

验证器默认绝不能自动解引用网络 $ref。即使确有获取必要，也必须显式选择加入，并配置主机允许列表、私有地址拦截和超时；本课的注册检查正是这样防御 SSRF。

</details>

## 5. 服务器因单工具速率限制被触发而拒绝调用，并希望模型能读取原因并作出调整。按照 2026-07-28 规范，哪种响应正确？

- **A** 返回使用错误码 -32042 的 JSON-RPC 错误，该代码在上一修订版中留给 elicitation
- **B** 返回内容列表为空且完全不含 isError 字段的正常结果
- **C** 返回使用旧式区段中自定义错误码 -32001 的 JSON-RPC 错误
- **D** 返回将 isError 设为 true，并在内容中说明原因的正常结果

<details>
<summary>查看答案与解析</summary>

**答案**　D

模型应能看到并调整的策略拒绝，例如速率限制或 rug pull 后暂扣，应放在带 isError 的工具执行结果中。不得在旧式 -32000 到 -32019 区段中新分配错误码；新实现应避免使用已有旧码 -32001。-32042 已随上一修订版的 elicitation 设计退役。

</details>

## 6. 同一网关后的两台独立 MCP 服务器都暴露一个字面名称为 search 的工具，彼此互不知情。网关向模型暴露这些工具前应做什么？

- **A** 用稳定的服务器标识符为各工具加前缀，避免名称冲突
- **B** 静默丢弃两个工具，直到其中一台服务器自行重命名
- **C** 把两个工具合并成一个条目，并从成功的调用中选取参数
- **D** 暴露最近一次发现调用中率先响应的那台服务器的 search 工具

<details>
<summary>查看答案与解析</summary>

**答案**　A

服务器名称不保证唯一。聚合器若让两个同名工具直接到达模型，就会产生工具遮蔽：本应发往一台服务器的调用可能被静默路由到另一台。标准解决方案是为每个聚合名称添加稳定的服务器限定前缀。

</details>
