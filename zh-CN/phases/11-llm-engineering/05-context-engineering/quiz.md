## 1. prompt 工程和上下文工程（context engineering）之间的区别是什么？

- **A** prompt 工程更高级
- **B** 它们是一回事
- **C** prompt 是用户的查询；上下文是模型窗口里的一切：system prompt、工具、检索到的文档、历史，以及 prompt 本身
- **D** 上下文工程是关于数据库设计的

<details>
<summary>查看答案与解析</summary>

**答案**　C

prompt 工程专注于打磨用户指令。上下文工程管理模型的整个输入：放什么进去、把什么挡在外面、按什么顺序，以及如何分配有限的上下文窗口。

</details>

## 2. 为什么上下文窗口中的顺序会影响 LLM 性能？

- **A** 不会——LLM 平等地处理所有 token
- **B** 字母顺序能帮助模型更快搜索
- **C** 顺序只对代码重要
- **D** LLM 有近因和首因偏差，对上下文窗口的开头和结尾给予更多注意

<details>
<summary>查看答案与解析</summary>

**答案**　D

研究表明 LLM 更关注上下文窗口的开头和结尾（「迷失在中间」现象）。把最重要的信息放在上下文的开头或结尾能提升利用率。

</details>

## 3. 一个编程助手用掉了 128K 上下文窗口中的 22,700 个 token。为什么预算管理仍然重要？

- **A** 128K 对任何用例都应该够用
- **B** 只有 prompt 重要
- **C** 长对话、大代码文件和检索到的文档会迅速填满窗口；没有预算管理，关键上下文会被截断
- **D** token 计数不准确

<details>
<summary>查看答案与解析</summary>

**答案**　C

22,700 个 token 是基线。50 轮对话会增加 3 万以上 token。检索一个大代码库会增加 5 万以上。工具调用结果还会再加。没有主动管理，窗口被填满，最旧的上下文就丢失了。

</details>

## 4. 对话历史的滑动窗口（sliding window）策略是什么？

- **A** 动态扩展上下文窗口
- **B** 把对话按固定大小的块处理
- **C** 把模型迁移到另一台服务器
- **D** 只在上下文中保留最近的 N 轮，丢弃更旧的轮次，可选地先对它们做摘要

<details>
<summary>查看答案与解析</summary>

**答案**　D

滑动窗口在上下文中完整保留最近的 K 轮对话。更旧的轮次要么被丢弃，要么被替换成摘要。这在保留最相关的近期上下文的同时限定了内存用量。

</details>

## 5. 上下文组装器（context assembler）应该如何在各组件之间分配 token？

- **A** 最小化 system prompt 的 token
- **B** 根据查询类型动态分配：简单问题需要更少的检索上下文，复杂问题需要更多，并始终为生成预留余量
- **C** 给每个组件平均分配
- **D** 总是最大化检索上下文

<details>
<summary>查看答案与解析</summary>

**答案**　B

一个简单的事实性问题可能只需要 500 个 token 的检索上下文。一个复杂的分析可能需要 1 万。好的上下文组装器动态调整分配，并始终为模型的回复预留余量。

</details>
