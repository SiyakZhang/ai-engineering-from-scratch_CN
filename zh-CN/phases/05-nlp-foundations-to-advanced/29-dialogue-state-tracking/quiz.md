# 对话状态跟踪 · 自测

每题先选答案，再展开解析。

## 1. 对话状态跟踪在多个回合间维护什么？

- **A** 仅一段自由文本历史
- **B** 对话的一个嵌入
- **C** 一个槽-值字典，表示用户当前的目标，并在每个回合后更新
- **D** 一份带词性标注的转录稿

<details>
<summary>查看答案与解析</summary>

**答案**　C

DST 维护一个结构化的槽-值映射，供后端据此采取行动。

</details>

## 2. 联合目标准确率（Joint Goal Accuracy, JGA）衡量什么？

- **A** 每回合延迟
- **B** 余弦相似度
- **C** 每个槽都完全正确的回合所占比例（全对或全错）
- **D** 平均槽准确率

<details>
<summary>查看答案与解析</summary>

**答案**　C

JGA 是每回合所有槽的严格匹配；按槽计的准确率更宽松。

</details>

## 3. 为什么每个回合从历史重新生成整个状态能自然地处理用户更正？

- **A** 读取完整历史让模型能重新推导出最终状态，包括 'actually...' 这样的更正，而无需显式的回滚逻辑
- **B** 它使用更少的 token
- **C** 它在 GPU 上运行
- **D** 它避免使用嵌入

<details>
<summary>查看答案与解析</summary>

**答案**　A

全历史重新生成通过从整段对话重新计算最终状态来吸收更正。

</details>

## 4. 哪个 2026 模式能用 5 行代码给出一个保证有效的槽字典？

- **A** BM25 检索
- **B** TF-IDF 分类器
- **C** LLM + Instructor + Pydantic schema，配合受约束或经校验的输出
- **D** 手写正则

<details>
<summary>查看答案与解析</summary>

**答案**　C

Pydantic schema + Instructor 会自动对照槽本体校验 LLM 的状态输出。

</details>

## 5. 为什么要给你的 DST schema 做版本管理？

- **A** 事后添加新槽会使较旧的训练数据失效，并破坏纵向评估
- **B** 提速收益
- **C** 减少 token 数
- **D** JSON 所要求

<details>
<summary>查看答案与解析</summary>

**答案**　A

未做版本管理的 schema 变更会悄悄破坏训练数据对齐和评估可比性。

</details>

## 6. 为什么对合规敏感领域的 DST 必须在 LLM 抽取之外包含一个基于规则的检查？

- **A** 规则是多语言的
- **B** 规则避免使用嵌入
- **C** LLM 更慢
- **D** 仅靠 LLM 的 DST 可能错误抽取破坏性参数（金额、账户、日期）；规则层强制确定性约束

<details>
<summary>查看答案与解析</summary>

**答案**　D

合规领域需要确定性的强制执行；规则能捕捉 LLM 引入的槽错误。

</details>

## 7. 通过 LLM 在每个回合重新生成状态有什么成本顾虑？

- **A** 余弦成本
- **B** 更多嵌入
- **C** 嵌入漂移
- **D** 每回合重新读取完整历史会带来 O(n^2) 的总 token 用量；要给较旧回合设上限或做摘要

<details>
<summary>查看答案与解析</summary>

**答案**　D

全历史重新生成的 token 用量随回合数呈二次方增长；给历史设上限或使用滚动摘要。

</details>

## 8. 为什么在破坏性后端操作之前需要显式的确认流程？

- **A** 即便是好的 DST 也有非零的槽错误率；确定性的确认可防止操作打到错误账户或错误金额
- **B** tokenizer 所要求
- **C** 确认能提升 JGA
- **D** 延迟

<details>
<summary>查看答案与解析</summary>

**答案**　A

破坏性操作需要用户确认，因为 DST 永远不可能零错误。

</details>
